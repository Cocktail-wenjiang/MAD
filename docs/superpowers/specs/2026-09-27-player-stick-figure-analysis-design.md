# 球员火柴人视频分析设计

## 目标

为羽球友的 AI 训练台增加离线视频姿态分析能力。用户上传一段 MP4 训练视频后，系统逐帧识别球员，保留原视频背景，在球员位置叠加 2D 火柴人、球员编号、检测置信度和中心标记，并提供可供前端展示的逐帧 JSON。

第一阶段只做球员姿态标注，不展示羽毛球轨迹，不擦除真人，不输出 3D 或生物力学结论。

## 现有基线与约束

- 复用 `SoloShuttlePose` 的 PoseDetect 流程和已有 Keypoint R-CNN 权重。
- 姿态结果使用 COCO 17 点：鼻、双眼、双耳、双肩、双肘、双腕、双髋、双膝、双踝。
- 沿用仓库的 16 条骨架边：头部、肩肘腕、肩髋、髋膝踝和左右肩连接。
- `SoloShuttlePose` 代码按 MIT 许可使用；产品文档和发布包保留版权与许可声明。
- `ShuttleSet/ShuttleSet22` 作为训练/评估数据来源时，保留数据集论文引用、数据来源和使用范围说明。原始视频与权重不提交到本仓库。
- 当前仓库是 UniApp 前端和 FastAPI 网关；分析服务应与现有聊天 Provider 网关解耦。

## 系统架构

```text
UniApp 选择 MP4
  -> POST /api/v1/pose/jobs (multipart)
  -> FastAPI 保存输入并创建 job
  -> Pose worker 逐帧运行 PoseDetect
  -> 过滤检测框/关键点并渲染 annotated.mp4
  -> 写 frames.jsonl、summary.json、job.json
  -> GET /api/v1/pose/jobs/{id} 轮询状态
  -> 前端播放标注视频并读取 summary
```

### 分层

1. **HTTP 层**：校验文件类型、大小和时长，创建任务，返回稳定的 job 状态。
2. **任务层**：为每个任务创建独立目录，记录 `queued/running/succeeded/failed`，保存错误码和进度。
3. **推理层**：加载一次模型实例，优先使用 CUDA，缺失 CUDA 时回退 CPU；按帧返回检测框、17 点关键点和置信度。
4. **渲染层**：复制原帧，叠加火柴人、中心圆点、`P{id} {score}` 标签；低于阈值的点不参与相关骨架边。
5. **结果层**：输出 MP4、JSONL 和摘要，HTTP 层只暴露受控的下载 URL。

第一版可以使用进程内后台任务作为 worker 适配当前开发环境；推理接口设计为独立函数，后续可迁移到 Celery/RQ 或独立 GPU 服务。

## 数据协议

任务创建返回：

```json
{
  "job_id": "pose-20260927-abc123",
  "status": "queued",
  "poll_url": "/api/v1/pose/jobs/pose-20260927-abc123"
}
```

任务状态返回：

```json
{
  "job_id": "pose-20260927-abc123",
  "status": "succeeded",
  "progress": 1.0,
  "input": {"filename": "practice.mp4", "duration_ms": 32000, "fps": 30},
  "outputs": {
    "video_url": "/api/v1/pose/jobs/pose-20260927-abc123/video",
    "frames_url": "/api/v1/pose/jobs/pose-20260927-abc123/frames",
    "summary_url": "/api/v1/pose/jobs/pose-20260927-abc123/summary"
  },
  "summary": {"frame_count": 960, "player_count_max": 2, "avg_confidence": 0.89}
}
```

逐帧 JSONL 每行包含：

```json
{
  "frame_index": 42,
  "timestamp_ms": 1400,
  "players": [
    {
      "player_id": 0,
      "bbox": [120, 80, 210, 440],
      "score": 0.94,
      "center": [225, 300],
      "keypoints": [[225, 101, 0.98], [218, 98, 0.91], [232, 98, 0.92], [210, 105, 0.88], [240, 105, 0.89], [198, 145, 0.96], [252, 145, 0.95], [184, 205, 0.93], [266, 205, 0.94], [174, 268, 0.91], [276, 268, 0.92], [208, 280, 0.95], [242, 280, 0.94], [202, 365, 0.9], [248, 365, 0.9], [194, 438, 0.88], [256, 438, 0.87]]
    }
  ]
}
```

`player_id` 在单个任务内按检测排序稳定分配；若检测短暂丢失，渲染层只跳过该帧，不伪造关键点。后续需要跨帧跟踪时再加入明确的 tracker，不把排序 ID 误称为长期身份。

## 前端体验

- 上传卡片：只接受 MP4，限制 100 MB/60 秒，显示已选文件和开始分析按钮。
- 分析中：显示进度、已处理帧数和可取消状态；轮询间隔从 500 ms 逐步退避到 2 s。
- 成功：展示标注视频播放器、平均置信度、检测到的最大球员数和下载按钮；默认不展示羽毛球轨迹。
- 失败：显示可读错误、重试入口；输入校验错误不创建任务。
- 结果说明：明确这是单机位 2D 姿态叠加，不代表 3D、生物力学、球速或医疗结论。

## 错误与资源策略

- `unsupported_media`：非 MP4、文件过大或时长超限。
- `model_unavailable`：权重路径不存在或模型加载失败。
- `decode_error`：视频无法打开或读取帧失败。
- `inference_error`：推理中断，保留日志但不返回半成品为成功结果。
- `storage_error`：输出文件写入失败。
- 输入与输出目录使用任务 ID 隔离；文件名采用服务端生成名，避免路径穿越。
- 第一版限制并发任务数为 1（开发默认），超过限制返回 `busy`；生产部署再接队列和 GPU 资源池。

## 验证策略

- 单元测试：输入校验、17 点边过滤、置信度/坐标序列化、任务状态转换。
- API 测试：创建任务、鉴权、状态轮询、成功结果 URL、失败错误码。
- 推理适配测试：使用短视频 fixture 或 mock PoseDetect，确认生成 MP4、JSONL 和摘要字段。
- 前端检查：上传校验、轮询完成/失败、播放器 URL 和结果摘要渲染。
- 手工验收：用一段合法的单打视频检查骨架是否跟随球员，关键点缺失时是否不画错误连线，CPU 环境是否能返回明确的低速提示。

## 非目标

- 不在第一阶段训练新的姿态模型；先验证已有权重在目标机位上的效果，再基于误检样本做微调。
- 不做真人抹除、人体分割、羽毛球追踪、球场单应性和击球事件展示。
- 不把原始 ShuttleSet 视频、权重或用户上传视频提交到 Git。
